# Python CPU solver

Рабочий код — `solver_python/`. Используются NumPy и Numba, float64, факторизованная схема с прогонками и **только якобиан Аракавы**. Порядок шага сохранён: функция тока → границы Тома → завихренность → невязки. Это псевдовремя, не физический нестационарный интегратор.

## Структура

```text
alex/
├── configs/
│   ├── pulsation_re260/
│   │   ├── pulsation_re260.yaml
│   │   └── README.md
│   ├── pulsation_re260_stabilized/
│   │   ├── pulsation_re260_stabilized.yaml
│   │   └── README.md
│   └── magnets_2x3_re260/
│       ├── magnets_2x3_re260.yaml
│       └── README.md
├── solver_python/            # решатель, анализ, рисование, тесты
├── solver_python_run/        # простые bash-запуски
├── results/<имя YAML>/
│   ├── binaries/            # снимки ALEXBIN1, источник, конфиг, невязки
│   ├── figures/             # графики, frames/
│   ├── videos/
│   ├── tables/
│   ├── stationary/          # начальное приближение для Ньютона
│   ├── newton/              # стационар
│   └── linear_stability/    # спектр и базис управления
└── legacy/                  # прежние CPU/GPU, скрипты, курсовая, материалы
```

Имя эксперимента определяется **именем YAML без расширения**. Например, `configs/test_case/test_case.yaml` пишет в `results/test_case/`. Поля `experiment` и `output.root` удалены: двух конкурирующих способов назвать расчёт больше нет. Пути к файлу источника и файлу стабилизации задаются относительно YAML. Рабочие конфиги не зависят от текущей директории запуска.

## Запуск

В `solver_python_run/settings.sh` заданы интерпретатор и выбранный `EXPERIMENT`. По умолчанию выбран `pulsation_re260`. Все физические параметры, сетка, шаг и число потоков находятся в YAML выбранного эксперимента.

```bash
bash solver_python_run/check.sh
bash solver_python_run/run.sh
bash solver_python_run/render.sh
bash solver_python_run/video.sh
```

`video.sh` строит кадры и три видео: ψ, ω, линии тока. Запуски работают из любой директории. Интерпретатор задан явно: `alex/../.venv/bin/python`. Зависимости перечислены в `solver_python/requirements.txt`; активный решатель не требует компиляции C++ или установки Torch.

Для продолжений можно передать существующему `render.py` `--time-offset 10`, чтобы подписи кадров и график невязок показывали общую τ. `--workers` управляет только процессами отрисовки, `--scale-file` принимает JSON с общими `psi_limits`, `omega_limits`, `speed_limits`. Использованные шкалы сохраняются в `figures/render_scale.json`. В трёх видео `_t30` применена одна шкала для всех экспериментов; она также фиксирована во времени. На кадрах ψ/ω стрелки — скорость, на streamplot фон — модуль скорости. Жёлтые крестики обозначают внутренние глобальные минимум и максимум ψ, а не все вихри. Анимация показывает эволюцию полей по псевдовремени; линии тока не являются траекториями частиц.

Прямой запуск:

```bash
../.venv/bin/python -m solver_python --config configs/pulsation_re260/pulsation_re260.yaml
```

Повторный запуск заменяет **только `binaries/` данного эксперимента**, если эта папка содержит результаты солвера. Графики, видео, стационары и моды остаются на месте; после изменения параметров их нужно пересоздать. Результаты постобработки предыдущего запуска автоматически не становятся результатами нового.

### Начальные поля из файлов

Без блока `resume` запуск начинается с обычных нулевых ψ и ω. Для загрузки полей задайте **оба** пути в том же YAML:

```yaml
resume:
  psi: ../../results/pulsation_re260_rhs/binaries/result_999999.bin
  omega: ../../results/pulsation_re260_rhs/binaries/result_999999.bin
```

Используется обычный `bash solver_python_run/run.sh`, дополнительных скриптов нет. Пути разрешаются относительно YAML. Это снимки ALEXBIN1: из первого берётся ψ, из второго — ω; файлы могут совпадать или быть разными. Сетка должна совпадать, значения — быть конечными, ψ на стенках — нулевой. Границы ω пересчитываются по загруженной ψ и стенкам из YAML, скорости строятся из ψ. Параметры задачи и управление берутся из текущего YAML, а не из исходного запуска.

Это загрузка начальных полей **с новым отсчётом псевдовремени от нуля**. `n_time_steps` — число новых шагов; при `fixed_steps` `t_max` также задаёт длительность нового участка. Например, для продолжения состояния с τ=10 ещё на 20 единиц при dt=1e-5 задайте 2000000 шагов: время в новых файлах будет от dt до 20. Исходные времена каждого поля записываются в `summary.json: initial_state`.

Файлы проверяются и читаются до замены `binaries/`, поэтому можно стартовать и из снимков собственного прошлого запуска. Их копии сохраняются как `resume.psi.input.bin` и `resume.omega.input.bin`. Для сохранения всей старой истории используйте другое имя YAML; исходный прогон автоматически не дописывается. `check.sh` проверяет также начальные поля. При использовании класса `Solver` напрямую вызывайте `load_initial_state()` после `warm_up()` и до первого шага.

## Эксперименты и анализ

- `pulsation_re260`: гармонический источник, область 1×0.5, сетка 201×101, Re=260, dt=1e-5, 10⁶ шагов.
- `pulsation_re260_stabilized`: те же параметры плюс −P(ω−ω*) в правой части, gain=1. Базис берётся из анализа `pulsation_re260`.
- `magnets_2x3_re260`: шесть точечных диполей; это модельная конфигурация, не параметры измеренной установки из статьи.

После базового расчёта:

```bash
bash solver_python_run/stability.sh
bash solver_python_run/compare.sh
bash solver_python_run/distance.sh
```

`stability.sh` анализирует выбранный в `settings.sh` эксперимент. Ньютон решает исходную стационарную систему в знаках Python-солвера. Анализ спектра исключает ψ через уравнение Пуассона: это спектр физической полудискретной системы, не матрица одного шага по псевдовремени. `compare.sh` и `distance.sh` явно настроены внутри на пару `pulsation_re260` / `pulsation_re260_stabilized`; нормы расстояния берутся по сохранённым снимкам.

Магнитные инструменты явно выбирают магнитный YAML:

```bash
bash solver_python_run/plot_forcing.sh
bash solver_python_run/verify_magnets.sh
```

Проверка поля использует тот же `forcing.py`, что решатель. Проверочный запуск сохраняется отдельно в `results/magnets_2x3_re260/verification/<дата>/`.

## Сравнение коррекций обеих компонент

Три конфига: `pulsation_re260_base`, `pulsation_re260_projection`, `pulsation_re260_rhs`. Параметры общие: 201×101, Re=260, dt=1e-5, миллион шагов от нуля. Базовый прогон переиспользован из `pulsation_re260` после точного воспроизведения первых 1001 шагов; происхождение записано в результатах.

```bash
bash solver_python_run/run_projection.sh
bash solver_python_run/run_rhs.sh
bash solver_python_run/projection_comparison.sh
```

Эти скрипты явно выбирают соответствующие YAML. Последний только анализирует готовые расчёты: общие графики и отчёт — `results/pulsation_re260_base/figures/projection_comparison.*`, коэффициенты — `projection_modes.png`, таблицы каждого расчёта — `tables/state_projection_history.csv`.

Конфиги с суффиксом `_t30` продолжают каждый из этих вариантов из его состояния при τ=10 ещё на 2000000 шагов. Для анализа готовых продолжений передайте существующему `solver_python/compare_projection.py` три соответствующих YAML через `--base`, `--projection`, `--rhs` и `--time-offset 10`. Смещение применяется только к таблицам и графикам; время в бинарниках и `summary.json` остаётся локальным. Дополнительных скриптов запуска нет.

```yaml
stabilization:
  file: ../../results/pulsation_re260_base/linear_stability/stabilization.npz
  components: state
  method: projection   # либо rhs
  gain: 1.0
```

Парные моды `(φ,η)` связаны дискретным Пуассоном `Δ_h φ+η=0`. Проекция ортогональна в невзвешенной евклидовой метрике объединённых внутренних узлов ψ и ω. Коэффициенты общие для обеих компонент и пересчитываются на каждом шаге относительно стационара.

- `projection`: обычный шаг → полное вычитание проекции из обеих компонент → границы Тома → исходные невязки. Следующий шаг использует исправленную пару. Множителя dt нет.
- `rhs`: проекция старой пары фиксируется в начале шага; в каждый из двух RHS входит `−dt*gain` соответствующей компоненты проекции до прогонок.

Для теста противоположного знака `method: rhs` допускает отрицательный `gain`:
`gain: -1` прибавляет `dt*P(z−z*)` в обе правые части при `components: state`.
`projection` по-прежнему требует gain=1. Конфиг `pulsation_re260_rhs_t30_test`
совпадает с `pulsation_re260_rhs`, кроме знака gain: нулевые начальные поля,
1000000 шагов до τ=10, без resume и магнитов. Суффикс t30 в тестовом имени
исторический и не задаёт длительность.

Это разные силы воздействия: результат не доказывает преимущества одного места внесения поправки при одинаковой интенсивности. Скорость по-прежнему вычисляется из ψ. Удаление проекции само по себе не доказывает решения исходных уравнений: смотрите обе невязки и расстояния. В графиках расстояния нормированы отдельно по полной сетке; это другая метрика, чем метрика проектора.

Старый YAML без новых полей оставляет только RHS-коррекцию ω. Спектр с управлением из `stability.py` относится именно к старому оператору `A−gain*Pω`; для парной коррекции его не используем. Парный базис получен из физических мод, не из спектра полного псевдовременного шага.

## Численные соглашения

### Дополнительные магниты и угловые вихри

`pulsation_re260_rhs_corner_magnets_t15` — отдельный опыт от нулевых полей
до τ=15 с прежним `gain=-1` и четырьмя постоянными диполями возле углов.
Подробная постановка и команды находятся в
`configs/pulsation_re260_rhs_corner_magnets_t15/README.md`.
Новый необязательный блок `magnetic_actuation` имеет магнитные параметры
как у `forcing: type: magnets` и обязательное `reference: base_forcing`.
Он добавляет магнитный источник только в RHS ω поверх основного источника
и модального управления. Исходный стационар и базис проверяются по базовой
задаче; они не объявляются стационаром/спектром дополненной задачи.
Невязки и `converged` по-прежнему относятся к базовым уравнениям без управления,
что записывается в summary. Поэтому разрешена только фиксированная длительность.
Магнитный источник отдельно записывается в `binaries/magnetic_actuation.npz`.
Это первый опыт с постоянным воздействием, без обратной связи по вихрям.
`python -m solver_python.corner_vortices --config <YAML> --reference <YAML>`
строит диагностику малых положительных угловых максимумов ψ по снимкам.
Пропуск означает отсутствие обнаруженного локального ядра в заданном окне,
а не доказанное исчезновение вихря; контур половины максимума не является
сепаратрисой.

### Знаки и схема

`u=ψ_y`, `v=−ψ_x`, `ω=−Δψ`; якобиан аппроксимирует `ψ_x ω_y − ψ_y ω_x`. Правая часть уравнения завихренности содержит `+J_A + S`. Смешанные поправки факторизации и согласованные границы промежуточной прогонки сохранены. Невязки измеряются для исходных уравнений без управления, даже когда оно включено.

Форсировка: `none`, `custom` с функцией `source(x,y,lx,ly)` или `magnets` со списком `[x, y, d, B]` в СИ. `B` — поле отдельного диполя на его оси в плоскости модели. Число магнитов произвольное. Для сравнения высот при фиксированном физическом магните нужно согласованно менять осевое B: это не остаточная индукция материала.

Потоки задаются через `execution.threads`; распараллелены только независимые линии прогонок. Для 201×101 обычно достаточно одного потока. Шаг, сетка, арифметическая точность и критерий остановки не меняются ради скорости; `fastmath` не используется.

Проверены переиспользование временных массивов проекции/невязок и объединение проходов по массивам. В чередующихся замерах на одинаковой сетке 201×101 устойчивого выигрыша не было: различия около 1% меняли знак между замерами. Эти изменения не оставлены в рабочей численной части. Файл `kernels.py` побайтово совпадает с версией до реорганизации; сетка, dt, число итераций и точность не менялись.

Контрольные 5000 шагов с управлением и без него воспроизведены побитово для ψ, ω и каждой пары невязок. Подробности: `legacy/maintenance/reorganization_report.json`, `after_benchmark.json` и `allocation_trial_benchmark.json` рядом с ним.

## Проверки и архив

Прототип подбора **конечных** магнитов запускается командой
`bash solver_python_run/design_magnets.sh`. Сейчас выбран YAML
`configs/magnet_placement_array/magnet_placement_array.yaml`; подробности в
соседнем `README.md`. Сравниваются 2–192 магнита 10 × 10 × 5 мм на 231 допустимом
месте, по omega-компонентам парных мод на исходной сетке. Допускается монтажная
рамка на 12 мм шире кюветы с каждой стороны. Результаты:
`results/magnet_placement_array/figures/magnet_layout.png`, `magnet_amplitudes.png`,
`mode_fit.png`, `count_comparison.png`; таблица — `count_comparison.csv` в корне опыта.
Независимые знакопеременные амплитуды ограничены для шара коэффициентов,
охватывающего сохранённый базовый расчёт. Ошибка формы для 192 магнитов 45.24%,
для всех мест 44.69%: существенный остаток сохраняется. Это геометрическая
аппроксимация, не проверка стабилизации. Старый опыт `magnet_placement_two` сохранён.
Основной солвер и прежний источник `forcing.type: magnets` не изменены: runtime
по-прежнему использует диполи. Этот YAML запускается только `magnet_design.py`.

```bash
bash solver_python_run/test.sh
bash solver_python_run/benchmark.sh
```

Тесты проверяют независимое плотное решение шага, знаки, сохранение стационара, Аракаву, магниты, управление, YAML и бинарные снимки. Дополнительный тест сравнивает с временной исправленной копией архивного C++; он требует компилятор и имеющийся в репозитории Eigen, но не является зависимостью решателя.

Все старые файлы перенесены без удаления. Журнал переноса — `legacy/maintenance/migration.json`, копия Python до реорганизации — `legacy/maintenance/before_cleanup/`. Старые документы и архивные bash содержат исторические пути и не являются рабочими точками входа.

Существующие снимки, JSON и сохранённые конфиги внутри перенесённых результатов сохранены как исторические записи: абсолютные пути в них могут отражать старую структуру. Для новых запусков используются только актуальные YAML из `configs/`.

## Что сохраняется в Git

В репозитории сохраняются исходники, рабочие YAML, документация, отчёты, итоговые графики и таблицы анализа. Расчётные снимки и массивы (`.bin`, `.npy`, `.npz`), последовательности кадров, новые видео, кэши и тяжёлые архивы остаются локально и исключены через `.gitignore`. Ранее опубликованные материалы сохранены в `legacy/`.

После клонирования базовый расчёт можно запустить с нуля. Для управляемых опытов сначала нужно получить соответствующий `stabilization.npz` этапом анализа устойчивости или перенести проверенный пакет; продолжения с `resume` дополнительно требуют указанные в YAML исходные снимки. Наличие сохранённых отчётов и графиков не означает, что эти расчётные входы включены в Git.
